# InventoryOS — Claude Code Instructions

## Project overview

InventoryOS is an internal Strickland Brothers operating platform. It consolidates and replaces numerous third-party SaaS tools. Modules cover inventory counting, ordering, location management (lookup, tank monitors, AM/RD lookup, exception reporting, location comms), outlier reporting, meeting notes, forms, marketing campaign planning, project task tracking, EOD review workflows, scheduling, month-end processing, department-scoped access control, and integrations (Monday.com, OneDrive, Azure/Microsoft sign-in, Droptop).

- **Repo:** https://github.com/originalkiser/InventoryOS
- **Branch:** `main`
- **Stack:** React 18 + TypeScript 5 + Vite 5 + TailwindCSS 3 + Supabase JS v2
- **Build:** `tsc && vite build` — TypeScript errors are CI failures
- **Dev server:** `npm run dev`
- **Tests:** `npm run test` (Vitest)

## Claude Code operating rules

1. **Make targeted changes only.** Read the files directly relevant to the task. Do not scan the whole repo.
2. **Inspect before editing.** Always read a file before modifying it.
3. **Reuse existing patterns.** Match the code style, component library, and hook patterns already in the file.
4. **No unrelated refactors.** Do not clean up, rename, or restructure code outside the task scope.
5. **No new dependencies without approval.** All additions to `package.json` require explicit user confirmation.
6. **No new hex colors.** Use existing Tailwind tokens only (see Brand section).
7. **Include loading and error states** in any new data-fetching UI.
8. **State files inspected and files changed** at the end of every response (see Final Response Format).
9. **Avoid `.schema('public')`** — PostgREST does not support the `Accept-Profile: public` header. Use bare `supabase.from()` only for truly public-schema tables (none currently exist in this app). All app tables use named schemas.

## Task execution workflow

For every task:

1. Restate the objective in one sentence.
2. Identify the smallest likely file scope before reading files.
3. Inspect only the files needed for that scope.
4. If the task touches database writes, identify the schema/table/columns before editing.
5. If the task touches UI, identify the existing component/style pattern before editing.
6. Make the smallest safe change.
7. Run or recommend the narrowest relevant validation:
   - TypeScript/build check for code changes
   - targeted test if one exists
   - manual UI test steps if no test exists
8. Do not continue expanding scope after the original task is complete.

If a task is ambiguous, make a conservative assumption and list it under Risks / assumptions instead of scanning broadly.

## Supabase architecture

The app uses **multiple Postgres schemas**. Never call `supabase.from()` for cross-schema tables — always use the cast pattern:

```ts
const sb = supabase as any
sb.schema('inventory').from('table_name')
sb.schema('core').from('table_name')
sb.schema('platform').from('table_name')
sb.schema('outlier').from('table_name')
sb.schema('forms').from('table_name')
sb.schema('marketing').from('table_name')
```

### Schema map

| Schema | Contains |
|--------|----------|
| `inventory` | counts, thresholds, orders, order_profiles, order_sessions, meeting_notes, projects, project_tasks, monthly_ending_balances, recount_requests/recount_product_snapshots, tank_monitors, droptop_sync_log, location_order_config, location_comms, exception_reports, exception_issue_option, global_products, product_id_mappings, uom_mappings, product_usage, **vendors**, **vendor_parts**, issue_categories/issue_statuses/issue_tracker_columns/issue_custom_values (issue *config*, not the issues themselves — see `platform.issues` below), field_definitions, data_source_links |
| `core` | **locations**, **tasks** (standalone user tasks — moved out of `inventory`), user_sidebar_prefs, user_feature_access, location_exclusions, location_supplemental, pos_location_map, company_holidays |
| `platform` | user_profiles, **issues** (moved out of `inventory`, now department-scoped), departments, user_department_memberships, schedule_events, event_checklist_items, app_settings, custom_columns/custom_values, attachments |
| `outlier` | report system: reports, report_entries, weeks, departments |
| `forms` | form builder + submissions: forms, fields, field_conditions, condition_rules, submissions, responses, assignments, score_streaks, form_department_shares |
| `marketing` | campaign planning: campaign_templates, campaign_template_tasks, monthly_plans, campaign_assignments, campaign_tasks; Menu Board: menu_board_packages, menu_board_quart_defaults, menu_board_quart_overrides, menu_board_shares, franchise_menu_shares, franchise_setup_links |
| `archive` | `deleted_rows` — every deleted row (as jsonb) from tables whose ids other records reference. Written only by an `AFTER DELETE` trigger; see below. |

**Deleted-row archive (`archive.deleted_rows`, migration `20260819_archive_deleted_rows.sql`):**
Cross-table references in this app are plain `uuid` columns with **no foreign keys**, so deleting a row (or clearing + re-uploading a table, which is a delete plus brand-new ids) silently orphans everything pointing at it — no error, it just stops matching. An `AFTER DELETE` trigger copies the full pre-delete row into `archive.deleted_rows` for the tables that carry that risk (`core.locations`, `core.pos_location_map`, `inventory.vendors`/`vendor_parts`/`issue_statuses`/`issue_categories`, `platform.departments`). Restore recipes are in the migration file's trailing comment — including the important case where rows were re-created under new ids, where the archive is used as an old-id → business-key map to repoint orphans rather than to re-insert. **When adding a table that other records will reference by id, add it to that trigger list.**

**Gotchas from recent schema moves — don't assume the old location:**
- `tasks` (standalone tasks) is in **`core`**, not `inventory`. `project_tasks` (project-scoped) is still in `inventory`.
- `issues` is in **`platform`**, not `inventory`. The issue *config* tables (`issue_statuses`, `issue_categories`, `issue_tracker_columns`, `issue_custom_values`) stayed in `inventory`.
- `exception_reports`/`location_comms` are separate but linked tables in `inventory` — a Location Comms row with `comm_type = 'Exception Reporting'` writes an `exception_reports` row too and stores its id in `exception_report_id`.
- `vendors` and `vendor_parts` moved from `core` to **`inventory`** (migration `20260818d_move_vendors_to_inventory.sql`) to match everything else they relate to (`global_products`, `uom_mappings`, `location_order_config`, `product_usage`). Before this move, a `.schema('inventory').from('vendor_parts')` query returned zero rows with no error rather than failing loudly, which let a real feature (Product Usage's vendor-part-number import) stay silently broken until caught manually — if you ever see a cross-schema table query return an empty result where you expected data, verify the schema against the file that actually owns/CRUDs that table before trusting this doc.
- `uom_mappings` moved from `core` to **`inventory`** (migration `20260821_orders_v2_uom_cost.sql`) — the *same* bug as the `vendor_parts` move above, on a different table: it was created in the original pre-schema-split `core` batch and never actually moved when `vendors`/`vendor_parts` did, despite the 20260818d migration's own comment claiming it was already in `inventory`. Nobody had verified it because the table was always empty, so the silent-zero-rows failure never surfaced. If a table's real schema location matters and it's unverified, query `information_schema.tables` rather than trusting this doc or a prior migration's comment.
- `global_products` moved from `core` to **`inventory`** (migration `20260824_move_global_products_to_inventory.sql`) — the *third* instance of this exact bug. The 20260818d migration's comment (quoted in the entry above) even lists `global_products` as one of the tables already correctly in `inventory` that `vendors`/`vendor_parts` needed to match — that claim was never true either. Every app reference (`GlobalProductsTab.tsx`, `NewOrderTab.tsx`, `useOrdersV2.ts`'s on-hand-unit conversion) already queried `inventory.global_products` and got silent empty results for it. Given this has now happened three times from the same original `core` batch, treat any *other* table this doc or a migration comment claims moved out of that batch as unverified until checked against `information_schema.tables`.

**RLS self-reference gotcha (hit `2026-09-10`, fixed by migration `20260922c`):** a policy's `USING`/`WITH CHECK` must never sub-`SELECT` the same table the policy is attached to — e.g. `(SELECT role FROM platform.user_profiles WHERE id = auth.uid())` inside a policy ON `platform.user_profiles`. Postgres 17 raises `42P17 infinite recursion detected in policy` the instant that branch actually executes. This can sit unnoticed for a long time: a row matching `id = auth.uid()` (editing your own row) short-circuits before that branch ever runs, so it only fires once someone acts on a *different* row — in this case it silently broke the entire admin "edit another user" flow from the `20260903e` RLS-initplan refactor onward. Use the existing `is_admin()` / `get_my_company_id()` `SECURITY DEFINER` helper functions instead, which read `user_profiles` without going back through its own RLS. If you're writing or auditing any policy and see an inline `SELECT ... FROM <the same table the policy is on>`, replace it with one of those helpers.

## Roles & department access

Roles (`src/lib/roles.ts`): `developer`, `administrator`, `area_manager`, `director`, `department_user` (legacy `admin`/`user` still handled for display).

- `isAdminOrDeveloper(role)` — developer/administrator/admin only.
- `department_user` role is scoped to specific departments via `platform.departments` + `platform.user_department_memberships`. `useDeptAccess()` (`src/hooks/useDeptAccess.ts`) returns the set of allowed sidebar section slugs for the current user, or `null` if unrestricted. A department's `slug` **is** the sidebar section key it gates — as of `2026-09-10` that's every top-level `Sidebar.tsx` section except the admin-only `global-config` (`inventory`, `droptop`, `data-connections`, `operations`, `marketing`, `finance`, `accounting`), plus a standalone `project_management` department that isn't its own sidebar section. `App.tsx`'s `SmartRedirect`/`DEPT_FIRST_ROUTE` sends department users to their first allowed section.
- The assignable list in the admin UI is **derived, not hardcoded**: `Sidebar.tsx` exports `ASSIGNABLE_SECTIONS` (built from `SECTION_ITEMS`), and `UsersPage.tsx`'s Manage User modal builds its "Section Access" checkboxes from that list — so a newly-added top-level sidebar section shows up there automatically. The first time an admin actually checks a section for someone, the save handler creates that section's `platform.departments` row on the fly (if it doesn't exist yet) before syncing the membership — no migration needed for sections added after `2026-09-10`.
- Manage departments/memberships in `src/modules/admin/UsersPage.tsx`.

## `platform.user_profiles` — critical rules

- **Email column is `email`**, not `work_email`
- **Active users:** filter with `.is('deleted_at', null)` — **never** `.eq('is_active', true)` (column does not exist)
- `user_profiles.id` IS the auth user ID — no separate join needed
- `preferences` (jsonb, migration `20260815_user_preferences.sql`) backs cross-device UI prefs via `useProfilePrefs` — dark mode, nav order, dashboard shortcuts, FAB state, hidden sidebar sections, Location Lookup panel view. Falls back to localStorage-only if the column is missing.
- New profile columns (`auto_push_tasks`, `skip_weekends_holidays`, `blocked_days`) may not exist in production until migration `20260628_eod_holidays.sql` is applied

```ts
const { data, error } = await (supabase as any)
  .schema('platform')
  .from('user_profiles')
  .select('id, full_name, email')
  .eq('company_id', profile.company_id)
  .is('deleted_at', null)
  .order('full_name')
```

## Defensive migration / decoupled save pattern

Some migration files in the repo root may not yet be applied to production. When a feature depends on a column that might be missing:

1. Save core required fields first — show error toast on failure and return
2. Save optional / new-column data as fire-and-forget best-effort
3. Never let a missing optional column break the whole workflow

```ts
const { error } = await sb.schema('x').from('table')
  .update({
    core_column: value,
    updated_at: new Date().toISOString(),
  })
  .eq('id', id)

if (error) {
  toast.error('Unable to save changes')
  return
}

// best-effort: new column that may not exist in production yet
sb.schema('x').from('table')
  .update({ new_column: value })
  .eq('id', id)
  .then(() => {})
```

**Files using this pattern:**
- `src/modules/operations/outlier/pages/ReportViewPage.tsx` — AM/RDO assignment columns
- `src/modules/meetings/MeetingNotesPage.tsx` — `links` column on `inventory.meeting_notes`
- `src/components/layout/Sidebar.tsx` — new profile columns (`auto_push_tasks`, etc.)
- `src/hooks/useProfilePrefs.ts` — `platform.user_profiles.preferences` (falls back to localStorage-only)
- `src/modules/tasks/TasksPage.tsx` — `core.tasks.target_date_end`
- `src/modules/schedule/ScheduleEventModal.tsx` — `platform.schedule_events.color`/`checklist_lead_days`, `platform.event_checklist_items.start_offset_days`/`end_offset_days`
- `src/modules/locations/LocationLookupPage.tsx` / config tabs — `core.location_supplemental` reads (best-effort/guarded)

### Custom Shop Config — `src/modules/locations/useCustomShopConfig.ts` / `CustomShopConfigPage.tsx` / `CustomShopConfigModal.tsx`

Per-shop exceptions that don't fit anywhere else (Price Per Quart, Included Quarts, Shop Supply Fee, Oil Inflation Surcharge, and whatever else an admin adds) — field *types* (`inventory.custom_shop_config_fields`) are admin-extensible, not a fixed column set; each shop gets a value per field it has a custom arrangement for (`inventory.custom_shop_config_values`), flagged to whichever package(s) it applies to (`inventory.custom_shop_config_packages`). Shared by the standalone page and Location Lookup's "Custom Config" box — both pass in the same `cfg`/`packageOptions` from their own hook instance rather than the modal fetching its own copy.

- **`per_package` (on the field type) — a field's value can vary by package or apply once per shop** (migration `20260930m_custom_shop_config_per_package_values.sql`). Price Per Quart/Included Quarts are `per_package = true` (a shop can price two packages' oil differently); Shop Supply Fee/Oil Inflation Surcharge stay shop-wide. `custom_shop_config_values.package_key` carries which package a per-package value belongs to — **`''` (NOT NULL, not a nullable column) for a shop-wide value**, deliberately: PostgREST's `.upsert(data, {onConflict: 'a,b,c'})` needs a real unique constraint on those literal columns, and Postgres treats every NULL as distinct from every other NULL, so a nullable `package_key` would have silently allowed duplicate shop-wide rows instead of upserting over the existing one — an empty-string sentinel plus a plain `UNIQUE (company_id, location_id, field_id, package_key)` sidesteps that entirely, same upsert shape as everywhere else in this app. `CustomShopConfigModal.tsx` renders package selection FIRST, then shop-wide fields, then a per-package-field block for each CHECKED package — needed that ordering since the per-package inputs literally can't exist until packages are picked.
- **Package options are Menu Board's own registry (`marketing.menu_board_packages`) UNIONED with every package Package Mapping has classified as Oil Change** (`inventory.droptop_package_classification`, `useCustomShopConfigPackageOptions()`, renamed from `useMenuBoardPackageOptions` when this changed) — originally Menu Board only, which meant only the ~5 canonical menu tiers were selectable; Package Mapping's oil-change list is the more complete, current one (also covers the cryptic legacy SKU codes and `"<Tier> Oil Change - <oil type>"` naming eras Menu Board never listed). Deduped by normalized display name so a package present in both doesn't show up twice — Menu Board's entry (nicer `package_key`) wins on a collision; a Package-Mapping-only entry is keyed by its own raw name (this column has always been a loose text tag, never a hard FK, so mixing key spaces here is safe).

### Procurement Deck — `src/modules/inventory/ProcurementDeckPage.tsx` / `src/modules/inventory/procurementDeck/`

Route `/procurement-deck` (Inventory sidebar section) — one tab per slide of the monthly "Procurement Update" exec deck (built from `Data for Month End Decks v10.10.2025.xlsx` + the July 2026 `Monthly Procurement Update` PDF), each with an editable table, a file upload to refresh it, and a chart matching the deck's own visual.

- **One flexible schema covers every slide shape** instead of a table per slide (migration `20260930n_procurement_deck.sql`): `inventory.procurement_deck_grid_cells` (row_label × col_key → value_num, a generic pivot — a month axis and a plain metric-name axis use the exact same shape, e.g. Oil/Part/Additive by month, or an Area Manager by Ordered/Invoiced/Received/Received%), `inventory.procurement_deck_kpis` (snapshot label/value tiles with no month axis — Contract to Date, Est Fulfillment, July Rebates), `inventory.procurement_deck_list_items` (ordered bullet text — Wins/Opportunities, shops still needing a recount). All three are keyed by `(company_id, slide_key, table_key, ...)` — `table_key` lets one slide hold more than one independent grid/kpi-group/list (e.g. Mighty Fulfillment's `afs`/`m5`/`top_af`/`bottom_af`/`top_caf`/`bottom_caf`).
- **Seed data is genuinely live where the workbook is live, PDF-only where it isn't** — several of the workbook's sheets (`Ending Balance-Add/Oil/Part`, `Net Adjust-*`, `ME Inventory Adjustments`, `Receiving Compliance`) are empty/stale pivot outputs that were never refreshed, so those slides (Recount Compliance by Area, Daily Month-End Count Compliance, Compliance Trends MoM, 3-Way PO Match, M5%, the Executive Summary KPIs/Wins/Opportunities, and July-only rebate figures) were hand-transcribed from the PDF's own printed numbers instead — both source files were treated as fair seed sources per the original request ("seed what you can from the files attached"), not the workbook alone. Ending Balance, COGS (via `COGS Recast`, not the shorter/staler `COGS Trend`), RD Gal Purchased, RD OTIF-Corp/FZ, RD Product Mix, VV Gal Purchased, Mighty Purchases, and Mighty AFS all came straight from the workbook and were cross-checked against the PDF's printed figures before seeding (exact matches).
- **`GridSection.tsx`** is the one reusable editable-table+chart+upload component behind every numeric slide — inline-editable cells (Template 2 shape, `onBlur`), an "Add Row" input, a per-row delete, and a `FileUploadZone` upload where the first column is the row label and every other header becomes a column (a header that parses as a month — `"Jul-26"`, `"2026-07"`, `"July 2026"` — lines up with the existing seeded column instead of appending a stray new one). `rowFormats`/`columnFormats` override the grid's own default `ValueFormat` (`currency`/`percent`/`number`/`gallons000`) for the one row or column that doesn't match the rest (e.g. Daily Count Compliance's `Percent Complete` row among otherwise-plain counts, PO Match Top/Bottom 3's `pct` column among dollar counts) — needed since a grid otherwise assumes one format for every cell.
- **`DeckChart.tsx`** renders the grid's own cells straight into a dark-navy-card `recharts` chart (stacked bar / grouped bar / line / bar+line combo, chosen per slide in `ProcurementDeckPage.tsx`) styled to match the deck's own dark chart cards.
  - **Uses the static `sb-navy`/`sb-cream` token namespace, not the dynamic `navy`/`cream` tokens** — found live 2026-09-15: the chart cards and KPI tiles used `bg-navy`, which is CSS-variable-backed and FLIPS in dark mode (`.dark` remaps `--color-navy` to a light blue-grey meant for *text* on a dark page, not a background — see `index.css`) — so in app dark mode the "dark" chart card rendered as a washed-out light box with low-contrast text, exactly backwards. This card is deliberately always-dark regardless of the app's own light/dark setting (it's recreating the PPT's fixed look, not adaptive app chrome), which is exactly what the pre-existing static `sb.*` Tailwind color namespace (`tailwind.config.ts`, "OutlierOS static color namespace") is for — `bg-sb-navy`/etc. never flip.
  - **Copy (Dark) / Copy (Light) buttons** put a real PNG screenshot of the chart on the clipboard for pasting into PowerPoint (`html2canvas`, already a dependency — same `useCORS`/`backgroundColor` pattern as Customer Heatmap's own copy button, including calling `navigator.clipboard.write()` *synchronously* in the click handler with a pending `Promise<Blob>` rather than an awaited one, so the async html2canvas capture doesn't outlast the browser's click "user activation" window). Dark reuses the already-mounted visible chart node; Light is a second, permanently-mounted-but-off-screen (`position:fixed; left:-99999px`, never `display:none`) instance of the same chart recolored for a white/cream slide background — recharts needs a real layout to render into, and toggling the *visible* chart's own theme just to screenshot it would flash. Light's palette reorders brand tokens so navy/inky (dark, high-contrast) come first and pale sky comes last, since sky reads fine on navy but nearly disappears on a light background.
  - **The chart's own pivoted data rides along as a second clipboard format** (`buildChartTsv()`, tab-separated, same image+text-together `ClipboardItem` pattern as Customer Heatmap's copy button) — a plain paste into PowerPoint still takes the image (richer formats win), but Paste Special → text (or pasting into Excel) turns it into a real editable table/chart with its own data labels, which a flat PNG can never offer. There is no way to make a browser clipboard write paste into PowerPoint as a native *chart* object directly — Office's live-chart paste only round-trips Office-to-Office; this TSV companion is the realistic version of "bring the data with it." Values are the same raw editable numbers a cell shows mid-edit (percent as `23.8`, not `0.238`), not the `$`/`%`-decorated display text, since the point is numbers something can still compute with.
  - **`referenceLines` prop** draws a dashed horizontal target line (see Tracking Periods below) via recharts' `ReferenceLine` — additive to whatever bars/lines the slide already plots, not a replacement for the seeded historical `Target` row.
- **Cells display fully formatted** (`formatValue()`, always exactly 1 decimal place, `$`/`%` per the field's own `ValueFormat`, comma grouping above 1000 via `toLocaleString`'s own default) rather than a bare number — an uncontrolled `<input type="text">` swaps to the plain editable number on focus (`toInputValue()`) and back to the formatted display on blur (`e.target.value` is set imperatively since a `defaultValue` input's DOM value doesn't otherwise track re-renders). `fromInputValue()` strips a stray `$`/`%`/comma defensively before parsing.
- **Per-grid period picker** (`GridSection.tsx`, All / Last Month / Last 3 / 6 / 12 Months / Custom) shrinks both the table's visible columns and the chart (and what a chart copy's TSV contains) to a trailing window — shown only when a grid's columns are actual months (`col_key` matches `YYYY-MM`), so it never appears on a metric-name grid like Top 3 Markets or Daily Compliance's Day 0..4. Defaults to "All" (today's un-filtered behavior) — purely an additive display filter, the underlying seeded history is never touched by picking a shorter window.
- **`KpiSection.tsx`**/**`ListSection.tsx`** are the same idea for the non-grid slide content — editable label/value tiles and editable ordered bullet lists (with up/down reorder), both add/delete-able since these change month to month (a new Wins bullet, a KPI that goes away). KPI tiles stay free-form text (`value_text`) — the `$`/`%`/decimal formatting above is grid-cell-only, since a KPI can hold anything from `"185 locations"` to a date range.
- **Field history + "changed this session" highlighting** (migration `20260930o_procurement_deck_history_periods.sql`, `inventory.procurement_deck_field_history`) — every time an already-filled grid cell or KPI value gets overwritten with something different (never on a first-time fill of an empty field), the OLD value is logged before the write. `FieldHistoryButton.tsx` is the small "i" button shown next to any field with at least one history entry — opens a modal listing past values with a Revert (writes the old value back as current, which itself logs a new history entry, same as any other edit). Separately, and NOT persisted anywhere, `useProcurementDeck`'s `changedThisSession` is plain React state — a field just edited during THIS visit gets the same orange-border treatment as Orders v2's `OVERRIDE_CELL` (`border-[#E67E22] bg-[#E67E22]/10` on the input directly, since these are inline inputs rather than plain table cells) until the page is reloaded. The two are independent: the "i" button can show up with no orange border (edited in an earlier session) and vice versa is impossible (a same-session edit of an already-filled field always logs history too).
- **Tracking Periods** (RelaDyne/Valvoline/Mighty Purchases only, `inventory.procurement_deck_periods`, `PeriodsPanel.tsx`) — each of these three slides tracks spend against a "Usage Period" and a "Contract Period", each a start month / end month / end-of-period target (native `<input type="month">`, one row per period_key, unique per `(slide_key, period_key)`). A period with a target set renders as a dashed `ReferenceLine` on that slide's own purchase-activity chart — this is the actual "are we pacing to hit the target" visual, additive to the existing historical `Target` series from the source workbook, not derived from it. Seeded Contract Period only (RelaDyne: Jul-25→Aug-27, $6M target from "twelve months into the agreement" + Est Contract Fulfillment; Valvoline: Oct-25→Sep-26, 300K target from the Year 1 contract extension; Mighty: Dec-25→Nov-26, $10M target from its own contract term KPI) — Usage Period is deliberately left unset since neither source file supports a confident guess at its start/end/target.
- Not yet verified in a live browser — this session had no login credentials for the deployed app; verified via `tsc --noEmit` + `npm run build` (clean) and a dev-server console check (no runtime errors through the login screen) only.

### Location Comms — `src/modules/comms/`

Log of shop/AM contacts. Two branches in `LocationCommsModal.tsx`: **Product Request** (products pulled from `location_order_config` for configured items, `product_usage` for non-configured; on-hand/days-of-supply read directly from `product_usage.days_of_supply`, not computed) and **Exception Reporting** (upserts an `exception_reports` row, stores its id back on the comms row). - **`LocationCommsModal.tsx`'s Cause Detail can now be typed in, not just picked** — Cause/Cause Detail come from `src/lib/causeTaxonomy.ts` (`CAUSE_CATEGORIES`/`CAUSE_SUBCAUSES`), a fixed lookup shared with Issues, NOT part of `comms_config` like Contact Method/Who/Type/Action Taken already were. A typed-in Cause Detail persists to a NEW `comms_config` bucket, `customCauseSubcauses: Record<string, string[]>` (keyed by Cause category, same shape as the fixed list it's merged with in the Combobox's options) via `useCommsConfig()`'s new `addCauseSubcause(category, value)` — scoped to Location Comms only; the shared `causeTaxonomy.ts` list itself is untouched, so Issues (if it uses the same taxonomy) doesn't see these custom additions.
- **The modal caches its own draft to `localStorage` while open** (added 2026-09-16) — an accidental backdrop click or Escape used to lose everything typed with no confirmation. Keyed per-record (`existing.id`) or per-shop-for-a-new-comm (`lockedLocationId`, so two different shops' "new comm" flows never collide) via `commDraftKey()`; every field change re-saves the draft (`draftFieldsJson` useMemo + a `useEffect` keyed on it), and opening the modal checks for a matching draft before falling back to `existing`'s own values, showing a dismissible "Restored unsaved changes" banner with a Discard action. Cleared on a successful save. Expires after 24h so a long-abandoned draft doesn't resurface confusingly. Doesn't attempt any conflict resolution against a since-changed server row — restoring local draft text always wins once saved, same as any other local-first draft.

  - **Undo/redo** — `src/hooks/useUndoableState.ts` is a generic drop-in `useState` replacement with undo/redo history (Ctrl+Z / Ctrl+Shift+Z + toolbar buttons); `FormBuilderPage`'s `fields` state now goes through it, so every field-list mutation (add/delete/reorder/duplicate/paste/property edit) is automatically undoable — including a bad `LocationSeeder` batch, since seeding just calls the same `onUpdate()` → `setFields()` path as everything else. A gap's resting height is a thin strip that grows (plain CSS `height` transition) into a full grey (`border-inky/50 bg-inky/10`) rectangle on hover — this single transition is also what makes the surrounding field cards visually "spread apart to make room": a preceding sibling's height animating smoothly reflows every later sibling's position in normal document flow each frame, no separate transform/animation needed on the cards themselves. `EmptyCanvasDropzone` is the same idea as `gap-0` for a form with zero fields, always mounted (not gated on a drag being in progress) so the empty-canvas message has something to show.   - **A real save-time race condition ate a brand new form's fields** (found + fixed 2026-09-16, live user report: "when I named it, it removed all the fields... that form wasn't in the list either") — `save()`'s CREATE path used to call `navigate(`/forms/${id}/edit`, {replace:true})` immediately after inserting the `forms.forms` row, THEN `await saveFormFields(id, fields, conditions)` afterward. ### Orders v2 — `src/modules/orders-v2/` (`engine.ts` generation, `useOrdersV2.ts`/`useOrderHistory.ts` persistence)

A bulk rule configured with `units_per_uom_gallons: 4` (1 order unit = 1 real gallon) is the standard/expected shape — with that, a bulk line's own `qty` already reads as real gallons directly, which is what lets `bulk_rounding_increment`'s "1 = whole gallons" documentation and the rule below both work in plain real-gallon terms without further conversion.

- **Bulk per-product minimum round-up threshold** (added 2026-09-16, migration `20260930u_bulk_minimum_threshold_and_line_note.sql`) — a bulk per-product minimum (`OrderMinimum.type` `'gallons_per_product'`/`'units_per_product'` on a bulk group, e.g. "55 gallons — a drum") used to always round a below-floor line up to the full minimum (`applyPerProductMinimum`). A vendor won't ship a partial drum, so `applyBulkPerProductMinimum` (bulk-only; package per-product floors still go through the original, unchanged `applyPerProductMinimum`) now only rounds up when the line's own calculated demand is at least `ctx.settings.bulk_round_up_threshold_gal` (a real per-company setting, default 35) — below that, the line is dropped entirely and reported in `GenerationResult.skipped` (reason `'below_bulk_minimum'`, same "Not ordered" card in `OrdersV2Review.tsx` every other skip reason already renders into) — **unless** the shop's current days of supply (`dos_before`) is already under `ctx.settings.bulk_urgent_dos_threshold` (default 15), meaning it would likely run low again before the next order cycle regardless, in which case the drum still goes out early. Both thresholds are editable on the Order Settings screen (a card that only appears when the Bulk minimum type is one of the two per-product types) rather than hardcoded, per an explicit ask to keep them tunable without a code deploy.
- **`GeneratedLine.note`** (free text, `null` otherwise) carries the specific numbers a fixed `LineFlag` badge can't — set to `"can order {X}, rounding up to minimum"` whenever the round-up above fires (alongside the new `'rounded_to_bulk_minimum'` flag), so the bump doesn't read as organic demand growth later. Persists through the whole lifecycle, not just the live generation run that created it: a `note` column was added to both `inventory.ov2_order_draft_lines` and `inventory.ov2_order_history_lines`, and the insert payloads in `useOrdersV2.ts`/`useOrderHistory.ts` (both explicit column whitelists, not blind spreads — a new `GeneratedLine` field needs to be added to each by hand or it's silently dropped before the DB call) now carry it through. Rendered right under the `Flags` badges in `OrdersV2Review.tsx`, `OrdersV2FinalReview.tsx`, and `OrdersV2History.tsx`.
- Tests: `engine.newrules.test.ts`'s `'bulk minimum round-up threshold (2026-09-16)'` block — the trick to hitting an exact calculated `qty` in a test is `daily_usage: 1` (so `dos_before === on_hand` directly) plus solving `days_of_supply_target` for the target calc, since `calc = (days_of_supply_target*daily_usage - on_hand) / gallonsPerUnit`.

### Droptop Purchase Orders — `supabase/functions/droptop-sync-purchase-orders/`

- **Missing `500` in `RETRYABLE_STATUSES`** (fixed 2026-09-16) — `droptop-sync-orders` added `500` to its own retry set on 2026-09-08 after a real incident (a generic Droptop-side "Internal server error" killed a location outright with zero retry); this function was written without picking up that fix and still only retried `429/502/503/504`. Now matches.
- **RESOLVED 2026-09-16 — the "13 of 279 shops" coverage gap was a real data-loss bug, not a shop-adoption gap.** After fixing `PoStatusPage.tsx`'s Inspect button (below) to actually scope to the selected shop, a live Inspect against shop "3" (Elkin, a "quiet" shop with 0 rows in the table) came back with real POs — `PO178`/`PO179`/`PO180`, `custom_po_id` `"3-09092026P"` etc. Cross-checking the table showed those exact same `po_id` values (`PO178`/`PO179`/`PO180`) already belonged to a completely different shop, "1521" (`custom_po_id` `"1521-07012026B"` etc.) — **Droptop's `po_id` is scoped per Droptop *operation* (per shop), not company-wide**, the opposite of what the sync function's own code assumed. Two bugs compounded on that wrong assumption: (1) the fetch-phase dedup Map was keyed by bare `po_id` across ALL locations, so shop 3's "PO178" and shop 1521's "PO178" collapsed into one in-memory entry before ever reaching the database; (2) the DB's own `UNIQUE (company_id, po_id)` constraint enforced the same wrong scope, so even without the Map bug the upsert would have overwritten one shop's row with another's. Net effect: every shop's Nth PO fought over the same table row as every OTHER shop's Nth PO, and whichever shop's sync happened to write last for a given number silently won — which is exactly why only a small, arbitrary set of shops (13) ever ended up with any surviving data, while Droptop itself had complete data for far more shops the whole time.
  - **Fix** (migration `20260930w_droptop_po_unique_per_location.sql` + `droptop-sync-purchase-orders/index.ts`): the unique constraint is now `UNIQUE (company_id, location_id, po_id)`; the in-memory dedup Map and the upsert's `onConflict` (and the items-linking `idByPoId` map, which had the exact same bare-`po_id` collision risk one step later) all now key on `${location_id}|${po_id}` instead of bare `po_id`. Deployed 2026-09-16.
  - **No historical data needed backfilling/repair** — this connection always does a fresh, non-incremental `daysBack: 180` pull from Droptop (Droptop remains the real source of truth; only OUR copy was corrupted by the collision), so a fresh **Sync Now** (or the next scheduled run) with the fixed code should populate all ~279 shops' real PO history correctly, no manual data cleanup required. **Not yet re-run as of this fix** — run Sync Now on `PoStatusPage.tsx` and re-check shop coverage (`SELECT COUNT(DISTINCT location_id)`) to confirm.
- **`PoStatusPage.tsx`'s "Inspect" button silently ignored the Shop filter** (found + fixed 2026-09-16, from a real user-supplied screenshot — this is what led to finding the bug above) — `inspectOne()` called the edge function with `{mode: 'inspect'}` and no `locationId`, so the function's own `locQuery` (which DOES support scoping by `locationId`) fell through to "every Droptop-enabled location" and inspected `locations[0]` — an arbitrary location the DB query happened to return first, unrelated to whatever shop was selected on screen. Fixed: `inspectOne()` now sends `locationId: fLocation`, the button is disabled until a shop is picked, and the result renders in an on-screen modal (operation id + a table of `po_id`/`custom_po_id`/`po_status`/`delivery_status`) instead of console-only.
- **This does NOT have the `MAX_LOCATIONS_PER_TICK`/incremental-catch-up pattern `runDroptopOrders`/`runDroptopTimeClock` have** — every scheduled tick re-syncs EVERY Droptop-enabled location's full 180-day history from scratch (chunked, but not incremental), rather than only touching locations that aren't caught up yet. Not changed as of 2026-09-16, since a PO's status can change well after its `created_timestamp` (unlike an immutable order/timecard row), so the same date-watermark approach orders/timeclock use doesn't map cleanly here — flagged rather than fixed, pending a decision on what "caught up" should even mean for a mutable-status record.
- **`custom_po_id` and the `note` field both carry OUR OWN `po_number`** when a shop enters it while creating/receiving a Droptop PO — confirmed against real production data: `custom_po_id` values like `"207-06222026P"`/`"1522-06302026B"` exactly match `poNumber()`'s own `{shop}-{MMDDYYYY}{B|P}` format (`engine.ts`), and a PO's own `note` field often reads `"SB PO #177-09152026P\nRD SO #1868148"` — embedding BOTH our po_number AND RelaDyne's own Sales Order number in one place. This is the join key for reconciling our own placed orders against Droptop's receiving data (see the RelaDyne open-order/invoice reconciliation work, if/when built) — not every Droptop PO necessarily has this (some show a RelaDyne invoice number or a bare digit string as `custom_po_id` instead), so treat a match as a positive signal, not assume every one of our orders has a corresponding Droptop PO.

### `useInventory()` — `src/hooks/useInventory.ts` (Dashboard, On Hand, `InventoryView`)

Module-level cache (`invCache`, 5-min TTL) shared across every consumer, backed by `fetchAll()` pulling the FULL `inventory.product_usage` + `location_order_config` tables (PostgREST's row cap means a single `.range()` isn't enough).

- **`fetchAll()` fetches pages CONCURRENTLY (count-first, then a bounded `PAGE_CONCURRENCY=6` worker pool), not one at a time** — found live 2026-09-16 investigating app-wide slowness (Location Comms' network tab showing dozens of `product_usage` calls, "are we checking every second??"): `product_usage` has grown to **~300,000 rows** (300 pages at 1000/page), and the original loop awaited each page in turn — 300 sequential round trips, each paying full PostgREST/network overhead on top of a query that's actually sub-10ms server-side (confirmed via `EXPLAIN ANALYZE`). `location_order_config` is much smaller (~5,200 rows, 6 pages) and was never the real problem.
- **`invFetchInFlight` de-dupes concurrent mounts of this same hook** — `KeepAlivePages.tsx` deliberately keeps the last 3 visited pages mounted in the background (see that file's own doc comment), so Dashboard, On Hand, and `InventoryView` can all be alive at once, each an independent `useInventory()` instance. Without this guard, the instant none of them has a warm cache (e.g. right after a hard refresh, or the 5-minute TTL just expired), **all of them raced their own full ~300-page pull simultaneously** — the actual mechanism behind "so many product usage pings," and a real contributor to the general slowness other pages (Location Lookup, Staffing Report) were experiencing that day, independent of the background Droptop backfill also running that same day (see its own note below) — two unrelated causes compounding on the same afternoon. A later mount for the same `companyId` now just awaits the one fetch already in flight instead of starting its own.
- **`fetchUsage()` scopes `product_usage` to configured products by default instead of pulling the full table** — found live 2026-09-15 confirming against production that only **54 distinct product ids** are ever referenced by `location_order_config` company-wide, matching **~7,300 of the table's 299,550 rows (97.5% was never configured anywhere)** — every other row was fetched, paginated, and shipped over the wire on every load purely so the "Only products in order config" toggle (`useInventorySettings.ts`) could be switched OFF to see it, a path confirmed to have never actually been used in production (the one company that had ever saved this setting had already turned it ON). `location_order_config` is now fetched FIRST (small/fast) specifically to build that product-id list, then `product_usage` is fetched with `.in('product_id', ids)` — the precise per-(location, product) narrowing still happens client-side via `orderKeys` in `rows`, unchanged; the server-side scope is intentionally the broader "used anywhere in the company" superset. Turning the toggle OFF is a genuine opt-in to the full unfiltered pull, unchanged from before. **`useInventorySettings.ts`'s own default flipped from `false` to `true`** to match — confirmed no company relies on "show all" as an explicit choice (the only saved row was already `true`), so new/untouched companies now get the fast path automatically. A side effect: while the toggle is on (now the default), the Dashboard's "Exclude categories" list is built from the scoped (configured-only) `usage` set rather than every category in the whole table — narrower, but every category it lists actually has visible rows, unlike before.
- **`useInventory({ auto: false })` skips the fetch-on-mount entirely** — added 2026-09-15 for the Dashboard specifically: even the now-scoped product_usage pull isn't worth paying on every Dashboard visit for a card most visits don't need. `loaded` (distinct from `loading` — false only while auto-load is skipped and nobody's asked yet) and `loadNow()` (a manual, cache-respecting trigger — `wantsLoad` ref flips true so a later companyId/onlyConfig change keeps refetching normally afterward, same as an eager consumer) are the two additions a lazy consumer needs. If a warm cache already exists for the current company+scope (e.g. On Hand was visited earlier this session), it's shown immediately regardless of `auto` — only a genuinely fresh fetch is skipped. `DashboardPage.tsx`'s Inventory Health / Days-of-Supply cards render a `LoadUsagePlaceholder` (a "Load Data" button calling `inv.loadNow()`) until `inv.loaded`. On Hand and the Location Lookup overlay's `InventoryView` both omit `auto`, so they keep loading eagerly — that data is the reason those pages are opened at all.

### Product Usage config tab — `src/modules/config/tabs/ProductUsageTab.tsx`

Same investigation, one more level: this tab's own `loadRpc()` paginates `inventory.product_usage`'s full company-wide table (299,550 rows as of 2026-09-15) via sequential keyset (`WHERE id > cursor`) pages — a real user-supplied `.har` showed 69 sequential GET+OPTIONS round trips over 20+ real seconds (reported as over a minute end to end). ### Background sync progress — `src/stores/syncTasksStore.ts` / `src/components/layout/SyncStatusWidget.tsx`

A long-running data pull (a Historical Backfill on Data Connections, in particular — can run for a long while across hundreds of shops) is a plain client-side async function, not a server-side job — but it's deliberately NOT tied to the page that started it. Progress is tracked in `useSyncTasksStore`, called via `.getState()` directly rather than a page-scoped hook, so it's plain module state rather than React component state for any one page. Combined with the Sidebar using `NavLink` (client-side route changes, no page reload), this is what lets a user start a backfill on Data Connections and freely navigate anywhere else in the app without interrupting it — the JS keeps running regardless of what's mounted. `SyncStatusWidget` (always rendered in `TopBar`, so visible from every page) is the one place that reflects it: click the small sync icon (left of Recent Pages) for a live list of running/recently-finished tasks with progress bars.

The one thing that doesn't survive is closing the tab, a hard refresh, or the computer sleeping — there's no server-side job behind this to resume from, so that outright kills whatever's running. `SyncStatusWidget` registers a `beforeunload` guard (browsers show their own fixed wording, not the custom message) while any task's status is `'running'`, specifically so a many-hour backfill doesn't silently vanish to an accidental tab close.

## Ordering logic — business rules

### Order date
- Order date = delivery day minus **3 business days** (excluding weekends)
- Thursday delivery → Monday order
- Monday delivery → Wednesday order
- Do **not** add holiday skipping to order date logic unless explicitly requested

### Product/order quantity
- Products may have `bulk_minimum`, `individual_minimum`, `unit_of_measure`, `order_uom`, `package_type`
- Use `global_products`, `vendor_parts`, `uom_mappings`, and `uom_thresholds` together when computing order quantities
- Do not assume all products order in the same unit of measure

### Keep-fill / VMI logic
- Keep-fill products must **not** be included in normal generated orders
- Use tank monitor data to estimate on-hand quantity when available
- If tank monitor data is unavailable, show an exception / needs-review state — never silently include or silently exclude
- Generate a side order, alert, or vendor notification recommendation
- Keep-fill logic must be visible and transparent to the user

M5%/HM Capture% are deliberately NOT computed here despite being technically buildable — doing so company-wide (every shop in the filter, not the single-shop gate M5%-by-weekday uses) would mean a per-shop package/vehicle fetch multiplied across potentially hundreds of shops; a **Placeholder Metrics** card lists these plus the sheet's other requested metrics with no real data source at all yet (% of Net Sales, Net Sales/Cars-per-Day Plan or PY Variance, R&P Total %, NPS %, Mgr Discount %, Inspections) and exactly what each would need.

Highlighting applies to the main shop×day matrix, plus a second "Flagged Shops" table below it showing only shops with at least one flagged day — **one row per shop** even when multiple days flag for it, same day columns, not one row per violation.
  - **Named-period labels show their resolved date range everywhere in the app**, not just here: `formatPeriodOptionLabel()`/`formatRangeLabel()` (`src/lib/datePeriods.ts`) turn "Last Week" into "Last Week (08/30-09/05/2026)" (4-digit year on both sides only if the range crosses a year boundary) — wired into the shared `PeriodPicker.tsx`, so Droptop Orders and Customer Heatmap picked this up automatically too, not just Staffing Report.

- **M5% and Package Mapping** (`src/modules/customers/PackageMappingPage.tsx`, route `/package-mapping`, Droptop sidebar section) — M5 = "Maintenance 5": Air Filter, Cabin Air Filter, Wiper Blade Replacement, Additives, Tire Rotation, tracked as additional-sale volume. **M5% = count of M5-classified package line items ÷ count of Oil-Change-classified package line items** (a package count, not an order count — one order can carry more than one of either), shown company-wide (Droptop Orders' stat row) and per-shop (its "By Shop" table's own M5% column).
  - Classification is by exact package **name**, in `inventory.droptop_package_classification` (migration `20260930d_droptop_package_classification.sql`, company-scoped) — **not** `financial_category_name`/`code`, which is confirmed **always null** on every real synced package in production (670k+ rows checked) despite existing as a field in Droptop's own API docs/webhook examples; the batch `get-orders` sync never actually populates it for this account. The classification enum was originally 3 buckets (`'oil_change' | 'm5' | 'none'`) — migration `20260930j_droptop_package_classification_m5_subtypes.sql` split the generic `'m5'` into its 5 specific sub-categories (`'air_filter' | 'cabin_air_filter' | 'wiper_blades' | 'additives' | 'tire_rotation'`, plus `'oil_change'`/`'none'`) once the Staffing Report needed each one's own percentage, not just one combined M5%. `isM5(classification)` (exported from `PackageMappingPage.tsx`) is what lets every existing "M5% = M5 ÷ Oil Change" computation (Droptop Orders, Staffing Report) keep treating all 5 as one bucket without caring which specific one a package is.
  - There is no package literally named "Oil Change" either — real package names span at least 3 naming eras (canonical menu tiers `Economy`/`Premium High Mileage`/`Premium Full Synthetic`/`Premium Full Synthetic High Mileage`; cryptic legacy SKU codes `SINS`/`EINS`/`FSDSYN`/`FS2`/`FSDB`/`FS3`/`FSE2`/`FFS`/`FS2D`/`FSE`/`FFS2`; and `"<Tier> Oil Change - <oil type>"` variants for Xpress/PLUS/Early Bird/Dexos). The migration seeds all of these (confirmed against real 2026-09-30 data) plus the 5 M5 categories — explicitly EXCLUDED from Oil Change: additive/top-off/flush/repair line items (`Engine Oil Additive`, `Top off Engine Oil`, `Complete Oil System Flush`, drain-plug repairs, `Diesel Oil Conditioner`, `Engine Oil Evacuation`) since those are add-ons, not the core service.
  - The Package Mapping page itself is the durable fix for "a package gets renamed or a new one is introduced" — it lists **every** distinct package name ever synced (via `get_droptop_package_name_counts()` RPC, a server-side `GROUP BY` — confirmed ~1.2s even at 670k+ source rows since the actual result is only ~80-100 distinct names; never pull all package rows to the client just to dedupe names, that would also silently truncate at PostgREST's row cap) with an inline classification `<select>` (Template 2 per `TABLE_TEMPLATES.md`) — anything not yet classified shows as "None" rather than being silently missing from the list.
  - **Clicking a shop row in the "By Shop" card opens Build Your Own Report pre-scoped to that shop** (sets `reportShops`/clears the other report filters/`reportMode('detail')`/opens the modal) — reuses the existing report modal entirely rather than a separate drill-down UI, since it already had exactly the shape asked for (configurable columns via checkboxes, order-level detail, export). Added an **M5% column** (`DETAIL_COLUMNS`, key `m5_pct`) to that modal — per-order M5 package line items ÷ Oil Change package line items on that ONE order (not "does this order have an M5 item"; an order with 2 M5 items and 1 oil change reads as 200%, matching the aggregate stat's own formula), showing `N/A` rather than `0%` when the order has no oil-change package at all. On by default alongside Packages/Quarts/Total.
  - **Location-list price mapping + pricing audit** (added 2026-09-19 follow-up, migration `20260930ae_droptop_package_price_audit.sql`) — `inventory.droptop_package_classification` gained a `price_column` column (nullable, `CHECK`ed to one of the 5 canonical `core.locations` columns) — a per-package-NAME mapping to which price column an oil-change package's `base_service_price` (Droptop Orders' own column, added 2026-09-17) should be checked against, since multiple raw names across the 3 naming eras can represent the same menu tier. Editable inline on this same page (a second `<select>` next to Classification, only enabled for `oil_change` rows). An **"Oil change packages only"** toggle (`Toggle`, filters both the classification table above and the audit table below by `classification === 'oil_change'`) is separate from — but commonly used alongside — this mapping.
    - **`get_droptop_package_price_audit(p_days int DEFAULT 7)`** (`SECURITY INVOKER` — an authenticated admin's own RLS on `droptop_order_packages`/`droptop_orders` already scopes it, same shape as `get_droptop_package_name_counts()`) returns one row per (shop, package name) actually sold in the window: the most common (mode) `base_service_price`, how many orders had that exact price vs. the total, and how many DISTINCT prices were seen. Deliberately covers **every** package regardless of classification ("having all the packages in there will be nice," per the request), not just oil-change ones — the oil-change-specific location-list comparison is a client-side overlay on top of this general table, using the page's own live classification/`price_column` state (not the audit RPC's own snapshot of it) so a mapping change shows up immediately without waiting on a refetch of the heavier audit query.
    - **`get_droptop_package_price_audit_orders(p_location_id, p_package_name, p_days)`** is the drill-down behind the "⚠ N prices seen" callout (shown whenever a package's distinct-price count is >1) — every order in the window for that exact (shop, package) pair, opened in a `Modal`.
    - **Pricing Exceptions** table below the main audit — one row per shop with at least one oil-change mismatch, columns for the 5 canonical packages (Droptop price next to list price), same shape as the Franchise tab's own pricing-discrepancy report (see that module's notes). If more than one raw package name maps to the same column for one shop (a rare cross-naming-era overlap), keeps whichever has more orders behind it for that cell.
    - Both RPCs and the `price_column` CHECK constraint verified directly against production: the audit query's own logic cross-checked against a raw manual run (4,322 real (shop, package) rows over the trailing week, 14 with genuinely multiple prices), the deployed RPC re-verified under a real authenticated role/JWT simulation (`SET LOCAL role = authenticated` + `request.jwt.claims`) rather than just as `postgres`, the drill-down RPC confirmed against one of those real multi-price rows (a $97.99/$89.99 split, a genuine real-world finding), and the `price_column` CHECK constraint confirmed to accept a valid value and reject a bogus one.

  - **Usage ledger**: `inventory.daily_product_activity.sold_qty` (the real day-by-day ledger — not `product_usage`, which only stores a rolling rate with no per-day history).
  - **Order data**: `inventory.droptop_order_services`' own nested `products` jsonb array (`{product_id, uom, quantity_total}`), fetched server-side via `get_droptop_order_product_sales(p_start, p_end, p_product_ids)` (join + `jsonb_array_elements` + date filter + `GROUP BY` shop/product/day, migration `20260930l_product_sales_history_order_services.sql`). **Not** `inventory.droptop_order_products` (the flat top-level table) — confirmed genuinely empty (0 rows) for this account, same distinction Droptop Orders' own Products column already had to make (see that file's own header comment: "most consumed products ... only ever show up inside services, not the flat top-level array") — a wrong-table assumption caught and corrected live after being flagged, real product_id overlap between the two sources confirmed (~1,527 of ~1,618-1,730 distinct ids each) before treating them as one coherent picture.

## Deployment

- **Live today: GitHub Pages**, via `.github/workflows/deploy.yml` (push to `main` → `npm run build` → `actions/upload-pages-artifact` → `actions/deploy-pages`), served at `originalkiser.github.io/InventoryOS/`. `vite.config.ts`'s `base` is `'/InventoryOS/'` when `GITHUB_ACTIONS` is set and `'/'` otherwise, so a Cloudflare or local build automatically gets the right base with no manual toggle. The workflow's `concurrency: {group: pages, cancel-in-progress: true}` means a deploy cancelled mid-flight by a fast-follow push can leave the Pages backend stuck ("due to in progress deployment") for up to ~90 min — it clears on its own, or can be cancelled manually in the Actions/Environments UI.
- Neither GitHub Pages nor Cloudflare Pages does server-side SPA routing, so a deep link (e.g. `/menu-board/4-a3f9`) needs the host to fall back to serving the app shell rather than a real 404. `vite.config.ts`'s `spa404Plugin` generates `dist/404.html` as an exact copy of the built `dist/index.html` on every build (`closeBundle` hook, alongside the existing `versionFilePlugin`) — no per-platform step required. **Do not reintroduce a hand-written `public/404.html`** — an earlier one used a GitHub-Pages-specific query-string encode/decode trick (`/InventoryOS/tasks` → `/InventoryOS/?/tasks`) that assumed the site always lived under a `/RepoName/` subpath; once the app moved to a root domain (`sboc.app`) that assumption broke catastrophically — each re-serve of `404.html` re-encoded the already-encoded query string, producing a runaway `?/&/~and~/~and~/~and~/...` URL that never resolved.
- **Live on Cloudflare Pages at `sboc.app`** (cut over `2026-09-12`; GitHub Pages at `originalkiser.github.io/InventoryOS/` still serves `main` in parallel until explicitly retired). The Cloudflare project was set up via the unified "Workers & Pages" dashboard, which is worth knowing about if you're ever troubleshooting it: that flow's "Create application" wizard creates a **Worker** by default (`wrangler deploy`), not a **Pages** project, no matter what deploy command you configure afterward — the actual Pages project has to be created separately via `wrangler pages project create <name> --production-branch=main`, and the CI's Deploy command must be `npx wrangler pages deploy dist --project-name=<name> --branch=main` (the explicit `--branch` matters: Cloudflare's build environment checks out a detached HEAD, so wrangler can't auto-detect the branch, and a deploy that doesn't match the configured production branch silently lands as a Preview deployment instead of Production — custom domains only ever serve Production). The API token used for the build also needs the **Cloudflare Pages: Edit** permission explicitly added — it's not implied by an account owner's Super Administrator role.
- Only 2 `VITE_*` env vars are actually read by the app: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. `.env.example` also lists some legacy/unused OneDrive/Droptop vars that nothing currently reads.
- **In-app 404** (`src/pages/NotFound.tsx`) is what `appRoutes.tsx`'s catch-all route renders for an unmatched authenticated path — SB-branded (droplet mark + brand tokens), replacing what used to be a silent `<Navigate to="/dashboard" replace />`. This is unrelated to `dist/404.html` above (the static host-level SPA fallback) — that file still has to stay an exact `index.html` copy so a nonexistent physical path can load the app shell at all; `NotFoundPage` only ever renders once the app has already mounted and React Router itself found no matching route.
- **Apple/Android "Add to Home Screen" icons**: `public/apple-touch-icon.png` (180×180), `public/android-chrome-192x192.png`/`-512x512.png`, and `public/site.webmanifest` — all generated from `src/assets/SBOC-IconCream.png` (the droplet mark) composited onto a solid navy square. `index.html`'s `<link rel="apple-touch-icon">`/`<link rel="manifest">` use Vite's `%BASE_URL%` placeholder (not a plain absolute path) so they still resolve under GitHub Pages' `/InventoryOS/` subpath, not just the Cloudflare root domain — but `site.webmanifest`'s own internal icon paths are plain absolute paths (`/android-chrome-192x192.png`), since it's a static JSON file Vite doesn't template; those are only guaranteed correct on the live `sboc.app` root domain.
- **Public, no-auth routes** bypass `RequireAuth` entirely in `App.tsx` and must never expose anything beyond what their own SECURITY DEFINER RPC returns (or, for forms, the existing `forms_read` RLS policy — see Forms module notes): `/f/:shareToken` (forms) on the main app domain; `/` (nearest-shop geolocation landing), `/:slug`, `/:slug/pdf`, legacy `/m/:token` (menu board share + PDF) on the separate `menu.sboc.app` subdomain (`MenuBoardApp`); `/:slug` (forms, customizable memorable link) on the separate `forms.sboc.app` subdomain (`FormsApp`, added 2026-09-17); `/:slug` (franchise menu board, always one locked shop, page 2 always hidden) and `/setup/:token` (franchisee self-service setup, added 2026-09-18 follow-up — open shop picker, reusable) on the separate `fzmenu.sboc.app` subdomain (`FzMenuApp`, added 2026-09-18) — each its own tiny router (`isMenuBoardHost()`/`isFormsHost()`/`isFzMenuHost()`, plain hostname checks) rather than routes registered alongside the main app, since a bare `/:slug` on the main domain would collide with every real app route. React Router matches the most specific path regardless of declaration order, so `/f/:shareToken` coexists fine alongside the authenticated `/*` AppShell splat.
- **`forms.sboc.app` needs to actually be added as a Cloudflare Pages custom domain (+ its own DNS CNAME) before the customizable form-URL feature works** — this is infrastructure, not code; nothing in this repo can provision it. Mirror whatever setup `menu.sboc.app` already went through on this same Cloudflare Pages project (Custom domains tab → add `forms.sboc.app` → DNS record, likely already auto-suggested since `sboc.app`'s zone is already on Cloudflare). Until that's done, `FormsApp`'s routing code is live but unreachable — a slug saved from the Share modal's Custom URL field just won't resolve to anything yet.

## Data safety rules

- **Never silently delete production data** — prefer soft deactivation (`deleted_at`, `active = false`)
- **Preserve source payloads** when importing external data (`raw_monday_data`, etc.)
- **Preserve audit fields** — `updated_by`, `last_change_source`, `updated_at`
- **Log sync summaries and errors** to the appropriate sync log table
- **Generated orders must be reviewable** before final submission unless the user explicitly approves auto-submission
- **Make exceptions visible** — missing data, unavailable tank readings, keep-fill items — never silently swallow them

## Things not to do

- **Do not reintroduce self-serve workspace/account creation.** A `/setup` self-serve signup page + a `completeSetup()` auto-heal path in `useAuth.ts` (any authenticated Supabase user with no profile row silently got a brand-new company created for them) were both removed for security — this app is Strickland Brothers-only, every real user is created by an admin via the `invite-user` Edge Function, which creates the auth user and the `platform.user_profiles` row together in one step. If `useAuth.ts`'s `loadProfile` ever encounters a session with no profile row (or a profile with no `company_id`), the correct behavior is to sign the user back out and show an error — never to auto-provision anything.
- Do not scan the whole repo by default
- Do not rewrite or restructure modules not directly related to the task
- Do not add new design colors or hex values
- Do not use `supabase.from()` (without `.schema()`) for any app table
- Do not use `.schema('public').from()` — sends an unsupported header to PostgREST
- Do not assume `platform.user_profiles.work_email` exists (column is `email`)
- Do not assume `platform.user_profiles.is_active` exists (use `deleted_at IS NULL`)
- Do not assume `tasks` is in `inventory` — it's in `core` (standalone tasks). `project_tasks` is still in `inventory`.
- Do not assume `issues` is in `inventory` — it's in `platform` (issue config tables `issue_statuses`/`issue_categories`/`issue_tracker_columns`/`issue_custom_values` stayed in `inventory`)
- Do not treat columns from pending (non-Uploaded) migration files as guaranteed in production — and don't treat root-migration-file location alone as proof a column is *missing* either; verify or use the decoupled save pattern
- Do not mix keep-fill products into standard order generation without special handling
- Do not hard-code Monday.com API tokens, Azure tenant/client IDs, OneDrive paths, or Supabase service-role keys — always use environment variables
- Do not introduce a new state management library (Zustand is already in use) without approval
- Do not add new `package.json` dependencies without explicit user confirmation
